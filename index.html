Project Overview

What did you actually build?

A full-stack web application that automates the entire job discovery and application process inside Facebook groups — from finding posts to writing and submitting personalised replies.

One-sentence summary — memorise this

"PropMate is an automated job application system that uses browser automation, semantic AI matching, and GPT-powered content generation to help users discover and apply to job opportunities posted in Facebook groups — with no repetitive manual effort."

🖥️

Frontend Portal

Next.js + TypeScript web portal — registration, CV upload, job preferences, and a dashboard to monitor applications and replies.

⚡

Backend API

Python FastAPI server handling all business logic, authentication, database operations, and REST endpoints.

🤖

Automation Engine

Playwright controls a real Chromium browser — logs into Facebook, scrolls groups, reads posts, types replies, and submits them.

🧠

AI Layer

Voyage AI produces embedding vectors for semantic job matching. OpenAI GPT generates unique personalised application comments per post.

🗄️

Data & Queuing

PostgreSQL stores all persistent data. Redis is the message broker. Celery schedules and executes automation tasks 5–6 times per day.

🐳

Infrastructure

Docker containers on Ubuntu behind an nginx reverse proxy. Tor anonymises traffic. Let's Encrypt handles HTTPS.

How the pieces connect — system architecture

The user's browser talks to the Next.js frontend, which calls the FastAPI backend over HTTPS via nginx. The backend stores data in PostgreSQL and publishes task messages to Redis. Celery workers consume those messages and launch Playwright, which opens a real browser, visits Facebook through a Tor proxy, and performs all scraping and posting. AI calls go from the worker to Voyage AI (embeddings) and OpenAI (comment generation). All services run as isolated Docker containers on a single Ubuntu server.

Technology Stack

Every tool, library, and language — explained

What each technology is, why it was chosen, and exactly what role it plays.

Frontend — the website users see
Next.js 15Framework
React-based framework for the web portal. Handles routing (each file in app/ becomes a URL), server-side rendering (pages pre-built on the server for fast loads), and optimised production builds. output: "standalone" makes Docker images small — no node_modules at runtime.
TypeScriptLanguage
Typed superset of JavaScript. You declare types — function getUser(id: string): User — and the compiler catches mismatches before code runs. Catches entire categories of bugs early and makes large-codebase refactoring much safer.
Tailwind CSSStyling
Utility-first CSS framework. Style with class names directly in HTML — class="flex gap-4 p-6 rounded-lg". The PostCSS plugin at build time scans JSX for used classes and generates only those rules — a tiny optimised output file.
ReactUI library
Core library Next.js is built on. Builds UIs as components — reusable pieces that manage their own state. When data changes, React re-renders only affected components — not the whole page. Fast and predictable.
AxiosHTTP client
Makes HTTP requests from the browser to the backend. Dashboard loads call GET /api/jobs to FastAPI and return JSON. Handles timeouts, errors, and authentication headers automatically via interceptors.
Backend — the server that powers everything
PythonLanguage
Primary server-side language — API, automation engine, AI integration, scheduling. Chosen because the AI/ML ecosystem (Voyage, OpenAI SDK) is Python-native; Playwright and FastAPI are Python frameworks; one language for all server-side code reduces complexity.
FastAPIWeb framework
Modern Python REST API framework. Routes requests to handlers, queries PostgreSQL, returns JSON. Fully async (using async/await) — handles many concurrent requests without blocking. Auto-generates interactive API docs at /docs.
PostgreSQLDatabase
Relational database — tables, rows, columns, foreign keys. Stores: users, encrypted credentials, scraped post history (SHA-256 hash unique constraint for deduplication), generated comments, reply statuses. Alembic manages schema migrations — schema changes apply to the live database without data loss.
RedisMessage broker
Ultra-fast in-memory store used as Celery's message queue. Celery Beat writes task messages to Redis; Workers read and execute them. A shared noticeboard between processes — one writes, another picks up. Also caches frequently-read data.
Celery + BeatTask scheduler
Celery Beat fires tasks at 1 PM, 3 PM, 5 PM, 8 PM, 10 PM. Celery Workers (two replicas) execute them — running the full scraping/classification/posting pipeline. FastAPI is never blocked. Failed tasks retry automatically.
PlaywrightBrowser automation
Controls a real Chromium browser programmatically. Opens Facebook, logs in, scrolls feeds, reads post text, types and submits comments with randomised delays. Runs headless on the server. noVNC switches it visible for manual CAPTCHA intervention.
Fernet encryptionSecurity
Symmetric encryption from Python's cryptography library. Facebook credentials are encrypted before PostgreSQL storage. The key lives only in the server's .env — not in code or the database. Decrypted in-memory only during login, then discarded.
Tor proxyAnonymisation
Routes browser traffic through anonymous relay nodes worldwide. Each circuit uses a different exit node — requests appear to come from different countries. One layer of the multi-layered anti-detection strategy.
AI & Machine Learning
Voyage AIEmbeddings
Embedding model tuned for professional text. Converts text to 1,024+ dimensional vectors encoding semantic meaning. Cosine similarity between job post and user profile vectors determines relevance. "React developer" correctly matches "frontend engineer" even with no shared keywords.
OpenAI GPTText generation
Generates personalised application comments via the OpenAI API. Receives: (1) system prompt with constraints, (2) user profile JSON, (3) job post text. Returns a unique tailored comment — under 150 words, professional, contextually specific. Azure OpenAI endpoint also supported.
Classification modelPost filtering
Two binary decisions: is this a job post? Is it relevant to this user's niche? Fine-tuned transformer (e.g. roberta-base) — cheaper at scale — or GPT zero-shot returning JSON label + confidence. Fine-tuning needs labelled data; zero-shot is flexible but costs more per call.
Reply classifierIntent detection
Labels recruiter replies: Interested / Needs more info / Not interested / Irrelevant. Only the first two trigger dashboard notifications — keeping the feed actionable and noise-free.
Infrastructure & Code Quality
DockerContainers
Each service runs in an isolated container. Docker Compose starts all containers together on a private internal network. Reproducible deployments, service isolation, easy targeted updates, smaller images via multi-stage builds.
nginxReverse proxy
Routes by URL path: /api/* → FastAPI (port 8000); everything else → Next.js (port 3000). Handles SSL termination, security headers, HTTP→HTTPS redirect, and optionally proxies noVNC through port 443.
ESLint + PrettierCode quality
ESLint statically analyses TypeScript/JavaScript for errors and style violations. Prettier auto-formats code consistently. Husky + lint-staged enforces both automatically on every Git commit — zero-warning tolerance.
System Workflow

From user sign-up to a recruiter reply

Complete end-to-end flow with details on what happens at each stage and which technology is responsible.

1
User registration & profile setup
User visits the Next.js portal and creates an account. FastAPI handles registration — passwords are hashed (bcrypt) before storage in PostgreSQL. The user fills a detailed profile: uploads their CV, enters skills, experience, and selects their job niche (e.g. Developer → React Developer). This profile is stored as structured JSON and becomes the context for all future AI calls.
2
Facebook credential storage (encrypted)
The user provides their Facebook login. Credentials are immediately Fernet-encrypted before being written to PostgreSQL. The Fernet key lives only in the server's .env. A noVNC session lets the user complete any required Facebook verification (2FA, CAPTCHA) once, establishing a persistent session cookie that is also encrypted and stored for future reuse.
3
Celery Beat fires a scheduled task
At configured times (1 PM, 3 PM, 5 PM, 8 PM, 10 PM), Celery Beat serialises a task message and writes it to Redis. A Celery Worker picks it up almost immediately. FastAPI is completely separate and never blocked by this heavy background work.
4
Browser automation — Facebook login
The worker decrypts credentials. Playwright launches headless Chromium routed through the Tor SOCKS5 proxy (port 9050). Navigates to Facebook, enters credentials, handles popups. If a stored session cookie is available, it injects it directly — skipping the login step entirely for speed and reduced detection risk.
5
Group membership check & join requests
For each of the 20–30 configured Facebook groups, Playwright checks membership status. If not a member, it clicks "Join Group". Groups with pending requests are skipped this run and retried in future runs. Only active member groups are scraped.
6
Post scraping & deduplication
Playwright scrolls each group's feed and extracts post text, author, URL, and timestamp. Each post URL is hashed with SHA-256 and checked against the ScrapedPosts table. If the hash exists, the post is skipped — O(1) lookup via database index. Posts older than 48 hours are also excluded.
7
Three-stage AI relevance classification
Stage 1 — Keyword pre-filter: Scans for job tokens. Eliminates ~85% of posts with zero API cost.

Stage 2 — Semantic embedding match: Posts and user profile embedded via Voyage AI. Cosine similarity calculated — posts below 0.70 threshold rejected.

Stage 3 — Fine-grained classifier: Makes the final call, catching niche distinctions embeddings may miss.
8
GPT-powered application comment generation
For each approved post, the worker calls OpenAI. The system message defines constraints: professional, specific, under 150 words, no generic openings, only relevant skills. The user message injects the user's profile JSON + the full job post text. Every post is different → every generated reply is naturally different → no bot signatures.
9
Comment posting via Playwright
Playwright locates the comment box and types the comment character-by-character with randomised delays (80–140ms per character), waits 1–3 seconds, then submits. Capped at 5–10 posts per run. CAPTCHAs or missing comment boxes cause the post to be skipped and flagged.
10
Activity logging & dashboard update
Each application is saved to the Applications table: post URL, comment text, timestamp, group name, status. The Next.js dashboard queries GET /api/applications and displays the full history, filterable by date, status, and group.
11
Reply monitoring & intent classification
Later runs check comment threads of previous applications for new replies. Each reply is classified: Interested → high-priority notification, Needs more info → medium priority, Not interested → archived, Irrelevant → ignored. Only actionable replies surface in the dashboard.
12
User manually takes over
Once a recruiter shows interest, automation stops for that thread and the user is notified with full context. All further communication is handled manually by the user on Facebook. The system got them to the door; the rest is human.
Algorithms & AI

The intelligence behind the system

Detailed breakdowns of every algorithm and AI technique — including the maths your examiner might ask about.

Job post search & matching — three-stage cascade
Stage 1 — Keyword pre-filter (rule-based)
Fast scan for job-related tokens: "hiring", "looking for", "apply now", "send your CV", "portfolio required". Token presence check — eliminates ~85% of posts instantly with zero API cost. Only posts with job-related signal proceed to the expensive AI stages.
Stage 2 — Semantic matching with Voyage AI embeddings
Posts passing Stage 1 are embedded via Voyage AI. The user's profile is also embedded (cached between runs). For each post vector A and user profile vector B:
similarity = (A · B) / (‖A‖ × ‖B‖)Values range from ~0.3 (unrelated) to ~0.95 (near-identical meaning). Posts below 0.70 are rejected. "React developer" and "frontend engineer" score ~0.88 with no shared words — the model understands meaning.
Stage 3 — Niche-specific classification model
Embeddings miss fine-grained distinctions — a "Graphic Designer" and "UI/UX Designer" post might both score 0.78 against a "Designer" profile. This stage makes the precise call: (a) fine-tuned transformer e.g. roberta-base trained on labelled posts — cheaper at scale, or (b) GPT zero-shot classification returning JSON label + confidence — no training data required but higher per-call cost.
Embeddings — intuition and maths
What is an embedding?
A 1,024-dimensional space where text is plotted as points. An embedding model is trained so similar-meaning texts cluster near each other — "software engineer" and "developer" are very close; "designer" and "carpenter" are far apart.

Why cosine similarity, not Euclidean distance?
Euclidean distance is dominated by vector magnitude — a long and short document on the same topic can be far apart simply due to length. Cosine similarity measures the angle — directional agreement independent of length. That is exactly what we want.

Examples:
"React developer" ≈ "frontend engineer" → ~0.88 → match ✓
"UI/UX Designer" vs "Graphic Designer" → ~0.74 → Stage 3 decides
"Software developer" vs "chef" → ~0.22 → rejected ✗
Application generation — prompt engineering
System message: "Write a comment under 150 words, specific to the job post, professional but conversational. Highlight only directly relevant skills. No generic openings. End with a clear call to action."

User message (injected JSON):{ "user_profile": { "name": "Ali Hassan", "skills": ["React","Next.js","TypeScript"], "experience_years": 3 }, "job_post": { "text": "Looking for a React developer for a 2-month project...", "group": "Pakistan Freelancers Network" } }Why unique results: Job post text differs every time → GPT output is naturally contextualised → every comment is different. Strict constraints push GPT away from repetitive templated responses that bot detection could pattern-match.
Duplicate prevention — SHA-256 hashing
Every scraped post URL is hashed with SHA-256 (256-bit / 64 hex char fingerprint) and stored in ScrapedPosts with a UNIQUE constraint + B-tree index.

SELECT 1 FROM scraped_posts WHERE hash = ? — O(log n) with index, effectively O(1) for our data sizes. SHA-256 is collision-resistant — computationally infeasible to find two different inputs producing the same hash, so false "already seen" matches are essentially impossible.
Anti-detection — layered strategy
1. Tor proxy — Different exit node per circuit, IP-based blocking becomes ineffective.
2. Rate limiting — Max 5–10 applications per run, 5–6 runs/day — far below thresholds.
3. Randomised typing delays — 80–140ms per character, mimicking human typing variance.
4. Post-action pauses — 1–5 second random delays between interactions.
5. Unique comment content — GPT-generated, contextually unique per post. No pattern for detectors.
6. Session cookie reuse — Avoids repeated login events that trigger security checks.
