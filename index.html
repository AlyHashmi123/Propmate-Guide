Project Overview

What did you actually build?

A full-stack web application that automates the entire job discovery and application process inside Facebook groups — from finding posts to writing and submitting personalised replies.

🎯 One-sentence summary (memorise this for your viva opening)

"PropMate is an automated job application system that uses browser automation, semantic AI matching, and GPT-powered content generation to help users discover and apply to job opportunities posted in Facebook groups — with no repetitive manual effort."

🖥️

Frontend Portal

A Next.js + TypeScript web portal where users register, upload their CV, set job preferences, and monitor applications and replies from a dashboard.

⚡

Backend API

A Python FastAPI server that handles all business logic, authentication, stores data in PostgreSQL, and exposes REST endpoints to the frontend.

🤖

Automation Engine

Playwright controls a real Chromium browser — logs into Facebook, scrolls group feeds, extracts post content, types replies, and submits them.

🧠

AI Layer

Voyage AI converts text into embedding vectors for semantic job matching. OpenAI GPT generates unique, personalised application comments per post.

🗄️

Data & Queuing

PostgreSQL stores all persistent data. Redis acts as the message broker. Celery runs tasks on a fixed schedule — 5–6 times per day.

🐳

Infrastructure

Everything runs in Docker containers on Ubuntu behind an nginx reverse proxy. Tor routes traffic anonymously. Let's Encrypt provides HTTPS.

🔗
How the pieces connect
High-level system architecture

The user's browser talks to the Next.js frontend which calls the FastAPI backend over HTTPS (proxied by nginx). The backend stores data in PostgreSQL and publishes tasks to Redis. Celery workers consume those tasks and run the Playwright automation engine which opens a real browser, visits Facebook through a Tor proxy, and performs all scraping and posting. AI calls are made from the worker to Voyage AI (for embedding) and OpenAI (for comment generation) over the internet. All services run as isolated Docker containers on one Ubuntu server.

Technology Stack

Every tool, library, and language — explained

What each technology is, why it was chosen, and exactly what role it plays in this project.

🖥️
Frontend — the website users see
Next.js 15
Framework
A React-based framework for building web applications. Handles routing (each file in the app/ folder becomes a URL), server-side rendering (pages are pre-built on the server for fast load times), and API routes. Used because it's the industry standard for production-grade React apps and has built-in support for TypeScript and Tailwind. The output: "standalone" config makes it deployable in Docker without needing a full node_modules folder at runtime.
TypeScript
Language
A typed superset of JavaScript. You declare the type of every variable and function parameter — function getUser(id: string): User. The TypeScript compiler checks these types before the code ever runs, catching entire categories of bugs early. For example, if you accidentally pass a number where a string is expected, TypeScript shows an error in your editor immediately. It also makes refactoring large codebases much safer because the compiler tells you everywhere a change has a knock-on effect.
Tailwind CSS
Styling
A "utility-first" CSS framework. Instead of writing separate CSS files, you style elements by adding short class names directly in the HTML — e.g. class="flex gap-4 p-6 rounded-lg bg-white text-sm". This makes UI development very fast, especially for responsive layouts. The PostCSS plugin compiles these class names into optimised CSS at build time, so the final CSS file only contains styles that are actually used — keeping it small.
React
UI library
The core UI library Next.js is built on. React builds interfaces as components — reusable pieces of UI (a button, a card, a form) that manage their own state. When data changes (e.g. a new job arrives), React automatically re-renders only the components that depend on that data — not the whole page. This makes UIs fast and easy to reason about.
Axios
HTTP client
A JavaScript library for making HTTP requests from the browser to the backend. When a user opens their dashboard and the app needs to fetch job history, Axios sends a GET /api/jobs request to the FastAPI backend and returns the JSON response. It handles things like request timeouts, error handling, and attaching authentication headers automatically via interceptors.
Lucide React
Icons
A library of clean, consistent SVG icons available as React components. Used throughout the dashboard UI — notifications, status indicators, navigation icons. Each icon is a tiny component: <Bell size={18} />.
⚙️
Backend — the server that powers everything
Python
Language
The primary language for the entire server side — API, automation, AI integration, and task scheduling. Python was chosen because: (1) the AI/ML ecosystem (Voyage, OpenAI SDK) is Python-native, (2) Playwright has excellent Python support, (3) FastAPI and Celery are Python frameworks. Using one language for all server-side code reduces complexity.
FastAPI
Web framework
A modern Python web framework for building REST APIs. When the frontend sends GET /api/jobs, FastAPI routes it to the right handler function, which queries PostgreSQL and returns a JSON response. FastAPI is fully async (using Python's async/await) so it can handle many concurrent requests without blocking. It also auto-generates interactive API docs at /docs using OpenAPI/Swagger — useful during development and for the developer to show clients what endpoints exist.
PostgreSQL
Database
A powerful relational database (tables, rows, columns, foreign keys — like a very powerful Excel). Stores all persistent data: users, encrypted Facebook credentials, scraped post history (with unique hash constraints to prevent duplicates), generated application comments, reply statuses, and notification records. Alembic is the migration tool — when a developer adds a new table or changes a column, Alembic generates a migration script that updates the live database schema without losing existing data.
Redis
Message broker
An ultra-fast in-memory key-value store used as the message queue between Celery Beat (the scheduler) and Celery Workers (the executors). When the scheduler triggers a job-scraping task, it serialises the task as a message and writes it to Redis. Workers continuously listen on Redis and pick up tasks to execute. Think of Redis as a fast shared noticeboard between processes — one process leaves a note, another picks it up. Redis is also used for caching frequently-read data to reduce database load.
Celery + Beat
Task scheduler
Celery is a distributed task queue for Python. It has two main parts: Celery Beat is the cron-like scheduler — it fires tasks at configured times (1 PM, 3 PM, 5 PM, 8 PM, 10 PM). Celery Workers are the processes that actually execute those tasks. When Beat fires, it writes to Redis; Workers pick up from Redis and run the full scraping/classification/posting pipeline. This decoupling means the main FastAPI server is never blocked by the heavy automation tasks. The system runs 2 worker replicas (as configured in docker-compose.prod.yml) so tasks can run in parallel for different users.
Playwright
Browser automation
A Microsoft-developed library that controls a real web browser (Chromium) programmatically from Python code. It can open pages, click elements, fill forms, scroll, read text content, and wait for page events — everything a human user can do, but automated. In this project it: opens Facebook → logs in with stored credentials → navigates to each group → scrolls the feed → extracts post text and metadata → posts generated comments. It runs in "headless" mode on the server (no visible window). The noVNC integration allows it to be switched to visible mode when the user needs to manually handle a CAPTCHA.
Fernet encryption
Security
Symmetric authenticated encryption from Python's cryptography library. User Facebook credentials are encrypted with a Fernet key before being saved to PostgreSQL. The key is stored only in the server's .env file — never in the codebase or in the database. When Playwright needs to log in, it decrypts the credentials in memory, uses them, then discards them. Even if the database were compromised, credentials would be unreadable without the encryption key.
Tor proxy (SOCKS5)
Anonymisation
The Tor network routes internet traffic through a series of volunteer-operated relay nodes worldwide. Playwright's browser is configured to use the local Tor SOCKS5 proxy (port 9050). From Facebook's perspective, requests appear to originate from an anonymous IP address that changes with each circuit. This is one layer of the anti-detection strategy alongside randomised delays, rate limiting, and human-like interaction patterns.
🧠
AI & Machine Learning layer
Voyage AI
Embeddings
An embedding model specifically tuned for professional/technical text retrieval. It converts any piece of text into a dense vector — a list of 1,024+ floating-point numbers that encodes the semantic meaning of the text in a high-dimensional mathematical space. Job posts and user profiles are both embedded. Matching is done by calculating cosine similarity between these vectors. Texts with similar meaning produce vectors that point in similar directions → high cosine similarity → strong match. This is why "React developer" correctly matches "frontend engineer" even though they share no keywords.
OpenAI GPT
Text generation
A large language model (LLM) accessed via the OpenAI API. Used to generate personalised job application comments. The system sends GPT: (1) a carefully engineered system prompt defining tone and constraints, (2) the user's profile as structured JSON, and (3) the full job post text. GPT returns a tailored comment — unique per post, under 150 words, professional in tone, mentioning only directly relevant skills. The Azure OpenAI endpoint option allows routing through Microsoft Azure for compliance or cost reasons.
Classification model
Post filtering
A text classification system that makes two binary decisions: (1) is this Facebook post a job offer? (2) is this job relevant to this user's specific niche and skills? This could be implemented as a fine-tuned BERT-family transformer (e.g. roberta-base fine-tuned on labelled job/non-job post data) or as zero-shot classification by prompting GPT to return a JSON label. The latter is simpler to build but more expensive per call. Both approaches output a label and confidence score.
Reply classifier
Intent detection
A multi-class classifier that analyses recruiter replies and assigns intent: Interested, Needs more info, Not interested, or Irrelevant. Implemented similarly to the job classifier — either a fine-tuned model or a GPT call with a structured prompt asking for JSON output. The output determines which replies surface as priority notifications in the user's dashboard and which are silently archived.

Infrastructure & DevOps
Docker
Containers
A containerisation platform. Each service (Next.js frontend, FastAPI backend, Celery workers, Beat scheduler, PostgreSQL, Redis, Tor proxy) runs in its own isolated container. A container is like a lightweight virtual machine — it has its own filesystem, dependencies, and networking, but shares the host OS kernel. Docker Compose defines how all containers start together, connect on a private internal network, and share volumes. Benefits: no "works on my machine" problems, easy rollback by pulling a previous image, and simple horizontal scaling.
nginx
Reverse proxy
A high-performance web server acting as the front door to the entire system. It listens on port 80 (HTTP) and 443 (HTTPS). Port 80 immediately redirects to HTTPS. On port 443, it uses the request path to decide where to forward traffic: /api/* → FastAPI on port 8000, everything else → Next.js on port 3000. It also handles SSL termination (decrypting HTTPS requests), so the internal services only deal with plain HTTP. Security headers (X-Frame-Options, etc.) are added here.
Let's Encrypt / Certbot
SSL/TLS
A free, automated Certificate Authority. Certbot is the client tool that requests an SSL certificate from Let's Encrypt for the domain, proves domain ownership, and installs the certificate into nginx. Certificates auto-renew every 90 days via a systemd timer. This is what makes the site load as https:// in browsers without a security warning.
noVNC
Remote browser
A browser-based VNC viewer that streams a remote desktop session through a WebSocket connection (ports 6080–6089). When a user needs to manually log into Facebook — to solve a CAPTCHA or approve a two-factor authentication prompt — the server's Chrome window is streamed to the user's browser. The user sees and interacts with the remote browser in real time, completes the authentication, and the automated session continues. Up to 10 concurrent sessions are supported (one port per session).
Ubuntu 22.04 LTS
OS
The host operating system on the deployment server. Ubuntu LTS (Long Term Support) releases receive 5 years of security updates — important for a production system storing user credentials. The server needs at minimum 2 vCPU / 2 GB RAM, with 4 vCPU / 4 GB recommended to handle multiple concurrent Playwright browser sessions alongside the web server and database.

System Workflow

From user sign-up to a recruiter reply — step by step

The complete end-to-end flow of the system, with details on what happens at each stage and which technology is responsible.

1
User registration & profile setup
The user visits the Next.js web portal and creates an account. FastAPI handles the registration request — passwords are hashed (bcrypt or similar) before being stored in PostgreSQL. After registering, the user fills in a detailed profile: uploads their CV/resume (stored as structured text in the database), enters their skills list, years of experience, work history highlights, and selects their primary job niche (e.g. Developer → React Developer) using a dropdown hierarchy. This profile becomes the context sent to all future AI calls.
2
Facebook credential storage (encrypted)
The user provides their Facebook login credentials through a secure form in the portal. On the backend, these are immediately encrypted using Fernet symmetric encryption before being written to the FacebookCredentials table in PostgreSQL. The Fernet key lives only in the server's .env environment file — it is never in version control and is invisible to developers. The system also starts a noVNC-accessible browser session so the user can complete any required Facebook verification (2FA, CAPTCHA) once, establishing a persistent session cookie that is also encrypted and stored.
3
Celery Beat fires a scheduled task
Celery Beat runs continuously and checks its schedule. At configured times (e.g. 1:00 PM, 3:00 PM, 5:00 PM, 8:00 PM, 10:00 PM) it serialises a task message — containing the user ID and task type — and writes it into the Redis task queue. A Celery Worker process (one of two replicas running in Docker) picks up the message almost immediately. This architecture means the FastAPI web server is completely separate from the heavy automation work and is never blocked or slowed down by it.
4
Browser automation — Facebook login
The Celery Worker decrypts the user's Facebook credentials from PostgreSQL using the Fernet key. Playwright launches a Chromium browser instance configured to route all traffic through the local Tor SOCKS5 proxy (port 9050). It navigates to facebook.com, enters the credentials, waits for the page to load, and handles standard post-login popups. If a stored session cookie is available (from a previous successful run), it may skip the login step entirely by injecting the cookie. This is significantly faster and reduces detection risk.
5
Group membership check & join requests
For each Facebook group in the user's niche mapping (20–30 groups per niche, pre-configured in the system), Playwright navigates to the group page and checks the membership status. If the user is not a member, Playwright clicks "Join Group" to send a join request. Groups with pending join requests are skipped in this run and retried in future runs. Only groups where the user is an active member are scraped. The group list is stored in the database, allowing users to suggest additional groups that are reviewed and added by an admin.
6
Post scraping & deduplication
For each accessible group, Playwright scrolls down the feed and extracts post data: post text content, author name, post URL, timestamp, and basic engagement counts. As each post is extracted, its URL (or content) is hashed using SHA-256 and checked against the ScrapedPosts table in PostgreSQL. If the hash already exists, the post is skipped instantly — O(1) lookup thanks to a database index. Only new posts continue to the classification pipeline. Posts older than a configurable threshold (e.g. 48 hours) are also skipped as they are unlikely to still be active opportunities.
7
Three-stage AI relevance classification
Stage 1 — Keyword pre-filter: A fast rule-based check scans the post for job-related tokens ("hiring", "looking for", "need a", "apply", "CV", "freelance", "portfolio required"). Posts without any of these are discarded immediately — no API calls needed. This eliminates ~85% of scraped posts cheaply.

Stage 2 — Semantic embedding match: The remaining posts are sent to Voyage AI to generate embedding vectors. The user's profile is also embedded (cached between runs). Cosine similarity is calculated between each post's vector and the user's profile vector. Posts below a similarity threshold (e.g. 0.70) are rejected.

Stage 3 — Fine-grained classifier: Posts that pass the embedding threshold go through a classifier that makes the final relevance decision — accounting for niche-specific distinctions that embeddings alone may miss (e.g. Graphic Designer vs UI/UX Designer posts both score highly against a "designer" profile but require different skills).
8
GPT-powered application comment generation
For each approved job post, the worker calls the OpenAI API with a carefully engineered prompt. The system message sets tone and constraints: professional, specific, human-sounding, no generic phrases, under 150 words, highlight only directly relevant skills. The user message injects structured JSON context: the user's full profile, skills list, top projects, and the complete job post text. GPT returns a unique application comment. Because the job post content differs every time, every generated comment is naturally different — avoiding the repetitive-text patterns that bot-detection systems look for.
9
Comment posting via Playwright
Playwright navigates to the job post URL, locates the comment input box, and types the generated comment character by character with randomised delays (e.g. 80–140ms per character) to mimic natural human typing speed. After typing, it waits a natural pause (1–3 seconds) before submitting. Each application session is capped at 5–10 job posts to stay well under any rate-limiting thresholds. If a post's comment box cannot be found or a CAPTCHA appears, the post is skipped and flagged for manual review.
10
Activity logging & dashboard update
Each successful application creates a record in the Applications table in PostgreSQL: job post URL, full generated comment text, timestamp, group name, group ID, and status (posted / failed / pending). The user's Next.js dashboard queries this table through the FastAPI GET /api/applications endpoint and displays the full history. The frontend can filter by date, status, and group. The user can see the exact comment that was posted for each application.
11
Reply monitoring & intent classification
In subsequent automation runs, Playwright revisits each active application's post URL and checks the comment thread for new replies since the last check. Replies are extracted and passed to the reply intent classifier. Classification output: Interested (e.g. "Please share your portfolio" / "Can we schedule a call?"), Needs more info (e.g. "What's your hourly rate?" / "Do you have experience with X?"), Not interested (e.g. "Position has been filled"), Irrelevant (spam, unrelated comment). Only Interested and Needs-more-info replies are stored as active leads and trigger dashboard notifications.
12
User manually takes over
Once a recruiter replies with interest, the system stops automating for that thread and sends a dashboard notification to the user. From this point, all further communication is handled manually by the user directly on Facebook. The system has done its job — it found the opportunity, applied intelligently, and identified the interested recruiter. The user takes it from there with full context of what was posted and what the recruiter said.
Algorithms & AI

The intelligence behind the system

Detailed breakdowns of every algorithm and AI technique — including the maths your examiner might ask about.

🔍
Job post search & matching pipeline
Three-stage cascade — fast to expensive, cheap to accurate
Stage 1 — Keyword pre-filter (rule-based)
The first pass is deliberately cheap. A set of job-related tokens (a curated list: "hiring", "looking for", "need a designer", "apply now", "send your CV", "portfolio required", "freelancer needed", etc.) is checked against each post's text using simple string matching. This is essentially a lookup against an inverted index built from the post tokens.

Why start here? Because embedding ~500 posts per run through Voyage AI has cost and latency. This filter eliminates ~85% of posts instantly — only the remaining ~15% that show any job-related signal go to the more expensive stages.
Stage 2 — Semantic matching with Voyage AI embeddings
Posts passing stage 1 are converted to embedding vectors using the Voyage AI API. An embedding is a list of 1,024+ floating-point numbers that encodes the semantic meaning of a text in a high-dimensional space — texts with similar meanings produce vectors that point in similar directions.

The user's skill profile is also embedded (this result is cached between runs to avoid re-computing it every time). Then, for each job post vector A and the user profile vector B, cosine similarity is calculated:
similarity = (A · B) / (‖A‖ × ‖B‖) The dot product measures how much the two vectors "agree" in each dimension. Dividing by the product of their magnitudes normalises it to the range [−1, 1]. In practice, for text, values range from ~0.3 (unrelated) to ~0.95 (near-identical meaning). Posts with similarity above a threshold (e.g. 0.70) proceed. The key advantage: "React developer" and "frontend engineer" score high similarity even though they share no words — the model understands synonymous concepts.
Stage 3 — Niche-specific classification model
Embeddings are excellent for broad semantic similarity but can struggle with fine-grained professional distinctions. A "Graphic Designer" post and a "UI/UX Designer" post might both score 0.78 against a "Designer" profile. This final stage makes the precise call.

The classifier is likely implemented as either:
(a) A fine-tuned transformer (e.g. roberta-base or distilbert-base) trained on a labelled dataset of job posts tagged with niche labels, OR
(b) Zero-shot classification via GPT — a structured prompt asks GPT to classify the post and return a JSON object with label and confidence score.

Option (b) requires no training data but costs more per call. Option (a) is more economical at scale but requires a labelled training dataset. The system's architecture supports either.
📐
Embeddings — the intuition and the maths
The most important AI concept in this project to understand
What is an embedding?
Imagine a giant 1,024-dimensional space (impossible to visualise, but mathematically straightforward). Every word, sentence, and document can be placed as a point in this space. An embedding model is trained on massive text corpora to learn where to place these points — such that texts with similar meaning end up geometrically close to each other.

Practical examples of what Voyage AI "understands":
• "React developer" ≈ "frontend engineer" ≈ "JavaScript developer" (very close)
• "UI/UX designer" ≈ "product designer" (close, but not identical to "graphic designer")
• "Full stack developer" vs "DevOps engineer" (moderately distant — related domain but different skills)
• "Software developer" vs "chef" (very distant)

Why cosine similarity and not Euclidean distance?
In high-dimensional spaces, Euclidean distance (straight-line distance) is dominated by the magnitude (length) of vectors, not their direction. A long document and a short document describing the same topic could be far apart in Euclidean space simply because one has more words. Cosine similarity measures the angle between vectors, which reflects directional agreement — i.e. topical alignment — independent of document length.

Application generation — prompt engineering
How GPT is instructed to write personalised, unique replies
System message (the persistent instruction to GPT):
"You are a professional job application writer helping a skilled freelancer apply for work. Write a comment that is concise (under 150 words), specific to the job post, professional in tone but conversational, and sounds like a real person — not a bot. Highlight only the skills directly relevant to this specific post. Do not use generic opening phrases like 'I am interested in your post'. Do not repeat information. End with a clear call to action."

User message (injected JSON context per application): { "user_profile": { "name": "Ali Hassan", "skills": ["React", "Next.js", "TypeScript", "Node.js"], "experience_years": 3, "top_projects": ["E-commerce platform", "SaaS dashboard"] }, "job_post": { "text": "Looking for a React developer for a 2-month project...", "group": "Pakistan Freelancers Network", "posted_at": "2024-01-15T13:42:00" } } Why this produces unique results: The job post text differs every single time, so GPT's output is naturally contextualised to each opportunity. Varying post text → varying context → varying output. The prompt constraints (no generic openings, specific to post, under 150 words) push GPT away from templated responses that bot detectors could pattern-match against.
🔒
Duplicate prevention — hashing
O(1) lookup to avoid reprocessing or reapplying to the same post
Algorithm: SHA-256 cryptographic hash

Every scraped Facebook post URL (or a combination of URL + content) is fed through the SHA-256 hash function, producing a fixed-length 256-bit (64-character hex) fingerprint. This fingerprint is stored in the ScrapedPosts table with a UNIQUE constraint.

Before processing any post, the system queries: SELECT 1 FROM scraped_posts WHERE hash = ?. With a B-tree index on the hash column (added automatically by PostgreSQL's UNIQUE constraint), this lookup is O(log n) in worst case, effectively O(1) in practice for the range of data sizes involved.

Why not just store the URL? URLs alone could theoretically be recycled or edited by the post author. Hashing the content too means semantically identical posts (even if reposted with a different URL) are detected. SHA-256 is used because it is collision-resistant — it is computationally infeasible to find two different inputs that produce the same hash output.
💬
Reply intent classification
Multi-class text classification on recruiter responses
Task type: Multi-class single-label text classification

Classes & examples:
• Interested — "Please share your portfolio", "Can we have a call?", "Send me your rate card", "DM me your details"
• Needs more info — "What's your availability?", "Do you have experience with e-commerce?", "What tools do you use?"
• Not interested — "Position has been filled", "We need someone onsite", "Budget doesn't match"
• Irrelevant — Someone else replying to the post, spam, unrelated comments

Implementation options:
(a) Fine-tuned BERT trained on labelled reply data — fast at inference, no per-call cost, but needs a labelled training set
(b) GPT zero-shot with JSON output — prompt asks for {"label": "interested", "confidence": 0.91} — flexible but costs per call

Only Interested and Needs-more-info classifications trigger user notifications. Not-interested and Irrelevant are archived silently. This filtering ensures the user's notification feed contains only actionable information.

Anti-detection strategy
How the system reduces the risk of Facebook identifying it as a bot
The system uses a layered anti-detection approach — no single technique is foolproof, but in combination they significantly reduce detection risk:

1. Tor proxy — Masks the server's real IP. Each Tor circuit uses a different exit node, making requests appear to originate from different countries.

2. Rate limiting — Maximum 5–10 applications per run, 5–6 runs per day = max ~60 applications per day. Far below thresholds that trigger automated detection.

3. Randomised typing delays — Comments are typed character-by-character at randomised human speeds (80–140ms per character) rather than pasted instantly.

4. Post-action pauses — Random 1–5 second pauses before and after key interactions (clicking, typing, submitting).

5. Unique comment content — Every comment is GPT-generated and contextually unique, avoiding the repetitive-text signature that bot detectors look for in comment patterns.

6. Session persistence — Reusing stored session cookies avoids repeated login events that could flag unusual account activity.

DockerfileDockerfile
Instructions for building the Next.js frontend Docker image. Uses a multi-stage build — a Docker best practice for minimal image sizes:

Stage 1 (builder) — Uses node:20-alpine as the base (a minimal Alpine Linux + Node.js 20). Copies package.json and runs npm ci (clean install from lockfile). Accepts a build argument NEXT_PUBLIC_API_URL which is baked into the built JavaScript bundle at compile time (this is how the frontend knows the backend URL — it cannot be changed after build without rebuilding). Runs npm run build to compile everything.

Stage 2 (runner) — Starts fresh from node:20-alpine (clean slate). Copies only the .next/standalone output and static files from stage 1. Sets NODE_ENV=production, PORT=3000, and HOSTNAME=0.0.0.0 (bind to all interfaces). The final image is tiny because it has no node_modules, no source code, no build tools. Starts with CMD ["node", "server.js"].

.gitignoreGit config
Tells Git which files and folders to never track or commit. Critical entries: .env (real secrets — must never be committed), node_modules/ (can be reinstalled from package.json — hundreds of MB), .next/ (compiled build output — regenerated by npm run build), *.log files, and OS-generated files like .DS_Store (macOS) and Thumbs.db (Windows). Configuration for lint-staged — a tool that runs linters only on Git-staged files (files you've added with git add). bun.lockbBinary lockfile
Bun's binary lockfile (not human-readable). Records the exact resolved version of every installed package and all their transitive dependencies. When anyone runs bun install, they get identical package versions regardless of when they install. This is critical for reproducibility — without a lockfile, npm install might resolve to a newer patch version of a dependency that introduces a breaking change. Binary format is faster for Bun to parse than JSON-based lock files.
package-lock.jsonJSON lockfile
npm's equivalent of bun.lockb — a JSON lockfile recording exact dependency versions. Used by the Dockerfile (which uses npm ci rather than bun for Docker compatibility). npm ci installs exclusively from the lockfile — it never resolves versions, just installs what's recorded. This makes Docker builds fully deterministic: the same image built today and in six months will have identical packages.
